## 1. 파일 구성

| `tf/rules.py` | 규칙(순수 함수): 지원 검사, 투표 판단, 필수 포함 역할 자리 계산, 배정안 검사 다섯 가지, 완전 탐색 배정, 배정 불가 이유 |

| `tf/jobs.py` | AI 배정 백그라운드 작업(1차→2차→3차→앱 자체 배정), 진행 상태 |

| `.github/workflows/keepalive.yml` | 매일 DB에 질의(일시정지 막기) |
| `tests/` | 연습용 시나리오, AI 실패 처리, 배정 탐색기, DB 제약, 화면 연기 시험 |

## 2. DB
공고 5장 최소 참고안을 따르고 다음을 더했다.
- `tf_teams.team_no`: 화면 key 의 팀 번호.
- `tf_applications`: 학생마다 `대기` 지원이 하나만 있게 부분 유일 인덱스.
- `tf_ai_logs`: 몇 차 모델이 어떤 이유로 실패했는지 기록.
- `tf_student_sub_roles.ord`: CSV의 보조 역할 순서를 보존.
- 모든 테이블에 RLS를 켜서 Supabase 공개 API로는 읽고 쓰지 못하게 함(앱은 테이블 주인 계정이라 영향 없음).

동시성: 지원은 학생 행 → 팀 행 순서로, 투표는 팀 행 → 지원 행 순서로 `select ... for update` 잠금을 잡고 검사한 뒤 기록한다. 그래도 겹치면 유일성 제약이 먼저 도착한 요청만 남긴다.

## 3. 주요 흐름
### 지원
1. 학생 행 잠금 → 마감, 이미 팀, 대기 지원 확인.
2. 팀 행 잠금 → 팀원 읽기 → `rules.join_problem`(꽉 참, 주 역할 중복, 필수 포함 역할 자리).
3. 막히면 기록하지 않고 "막힘: 이유". 빈 팀이면 승인과 팀원 추가, 아니면 대기.

### 투표
1. 마감이면 막힘. 팀 행과 지원 행 잠금, 지원이 대기인지 확인.
2. 투표자가 지금의 팀원인지, 이미 투표했는지 확인(투표는 바꿀 수 없음).
3. 거부가 하나라도 있으면 거절. 지금의 팀원 모두가 찬성이면 `rules.join_problem` 으로 재검사 후 승인 또는 거절. 아니면 대기.

### AI 배정
1. 마감 여부, 확정 여부 확인.
2. `rules.solve` 로 규칙을 지키는 배정이 있는지 먼저 확인. 없으면 `rules.diagnose` 의 이유를 `assign_status` 에 보여 주고 AI를 부르지 않음.
3. 있으면 백그라운드 작업 시작: 모델마다 요청 스레드를 띄우고 부른 쪽은 120초만 기다림. 요청 스레드도 응답을 조각으로 받으며 같은 마감 시각을 넘으면 멈춤. 응답 없음, 429 등 오류, 빈 응답, JSON 형식 오류, 검사 실패는 모두 다음 모델로.
4. 3차까지 실패하면 2번에서 찾은 배정을 씀. 최악의 경우 120초 × 3 = 6분 안에 끝남(10분 제한 안).
5. 화면은 3초마다 작업 상태를 읽어 "2차 모델(…)의 응답을 기다리는 중 · 35초 지남"을 보여 줌.
6. 확정할 때 지금의 DB로 다시 검사하고 한 트랜잭션으로 저장.

## 4. 시험

| `tests/test_scenarios.py` | 연습용 쉬움·중간·어려움을 단계마다 실행해 첫 단어 비교, 확정 뒤 규칙 검사. 투표 바꾸기, 팀원이 아닌 사람의 투표, 꽉 찬 팀, 마감 뒤 투표, BOM CSV, 관리자 계정 유지 | 실제 PostgreSQL 16에서 모두 통과 |

## 6. 알려진 한계(배포 뒤 직접 확인할 것)
- AI 배정 진행 상태는 앱 프로세스의 메모리에 있다. 배정 중에 Streamlit Cloud가 앱을 다시 시작하면 진행 상태가 사라지므로 "AI 배정"을 다시 눌러야 한다(DB의 상태는 그대로).
- AI 배정 단추의 결과 안내 "승인"은 작업을 시작했다는 뜻이고, 배정안은 진행 안내에 나온 뒤 확정 단추가 나타난다.
- 이 작업 환경에서는 Streamlit을 설치할 수 없어 진짜 브라우저 시험을 하지 못했다. 배포 앱에서 연습용 시나리오를 직접 해 봐야 한다.
